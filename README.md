## Rules that will bite

- **One challenge per team, and the choice is final.** Only the team lead of a team marked ready can select, Friday 15:00-17:30. No changes, no cancellations.
- **The roster also locks.** After the lead marks the team ready, nobody can be added, removed or swapped. Form the team in sinceai.app before Friday if possible.
- **Friday check-in is required, in person, by every member.** Browsing the app from elsewhere is not check-in. A member without a check-in or an approved Saturday arrival can be removed from the team overnight by the organisers.
- **On site only.** There is no remote participation.
- **The submission platform is sinceai.app, not Devpost.** An entry on Devpost alone is not a submission.
- **The deadline is fixed:** Sunday 8 November 10:00 EET. Submit early. Uploads attach to a saved submission, so create the entry before adding files.
- **AI tools are allowed and encouraged.** Using AI, even for most of the code, does not count against the team. What counts is understanding the system, the working product and responsible data handling. The submission form asks which GenAI tools were used and how.
- **Separate pre-existing work from what was built at the event.** Commit often with meaningful messages, and keep the README reproducible.
- **The repository has to be openable by judges.** Check the repo and demo links while logged out. A private repo is fine only if evaluators can open it.
- **IP terms vary by challenge.** Some transfer the new work to the company, others let the team keep ownership and grant a licence. Every member must accept the terms personally before the team can submit.
- **No ZIP archives.** Share code through the repository link.
- Under 18: contact info@sinceai.fi before the event.

What makes a strong entry, in the organiser's words:

- A working prototype, a live demo, or clear steps to run it. The product is the pitch.
- A repository with the actual project, a README and setup instructions.
- A short demo video, about two minutes. Recommended, not required.
- A concise deck only if it helps. It never replaces a working prototype.

## How we get judged

Each challenge company evaluates its own challenge and picks its top three. Evaluators weigh:

- Whether it works and actually answers the challenge.
- Real-world relevance and business value.
- Technical quality and feasibility.
- How well the team understands and explains the system.
- Responsible handling of privacy, security and data.

The five finalists are not picked by the companies. They come from the **participant vote** on Sunday morning: 10:00-12:00, 20 comparisons per builder, one finalist per different challenge. So the submission text and the demo video also have to convince 1,000 other builders who are not domain experts. Then the finals jury picks the overall winner from the five live pitches.

## What the repo README must contain at submission

The judging guide explicitly asks for a repository with a README and setup instructions, and recommends a short technology inventory. Keep this list next to the file:

- One paragraph on the problem and who has it.
- One paragraph on what the solution does, and a screenshot or GIF near the top.
- Setup and run steps that work from a clean clone, including environment variables and a sample `.env.example`.
- The demo path: what to click, what to type, what to expect.
- Technology inventory: AI tools and models used, frameworks and libraries with licences where it matters, third-party datasets and services, pre-existing code and assets kept apart from event work, and the security and privacy considerations.
- What is mocked, what is real, and what we would do with more time.
- Licence.
