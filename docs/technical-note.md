# PlantPilot technical note

PlantPilot turns a supplied Gaussian splat capture into a framed, mapped and navigable plant scene, plans a route to the faulty target and shows a grounded diagnosis on arrival. It runs offline: Python for the pipeline, a browser for the room view.

## 1. Problem and scope

The brief describes plant context fragmented across space, condition data and documents, and raw captures with no meaning: no walkable floor, obstacles or machines. The demonstrator must frame assets, map the builder pack, plan a collision-free route to the faulty target, highlight nearby assets and deliver cited guidance on arrival. Scope: one static floor, offline. `Industrial Boiler Room (1).ply` is damaged, `Equipment Room.ply` is complete, both run the same stages.

## 2. Pipeline

Modules: `app/server/src/plantpilot/`.

- Ingest: `splat.py`; PLY to `scene.npz`; contiguous sane prefix, 2,000,000 gaussian budget.
- Extract: `segment.py`; `scene.npz` to `objects.json`; 4 cm band, up to 16 planes with separate horizontal and vertical budgets, voxel `max(3 cm, 1.4 x spacing)`, gap then neck then quota split, floor completion, 150 cap.
- Name: `classes.py`; `objects.json` in place; context rules and fused instances, no geometry.
- Pack: `pack.py`; workbook to `pack.json`; P-005 target.
- Map: `mapping.py`; pack, objects to `mapped.json`; 0.7 class plus 0.3 size prior, 0.6 and 0.5 gates.
- Route: `scripts/make_route.py` and `nav.py`; scene, objects and mapping to `route.json`; 0.10 m grid, 0.55 m body, floor and near-vertical-surface layers, 0.20 m radius plus 0.02 m margin, A*.
- Diagnose: `diagnose.py`; pack to `diagnosis.json`; joins by `asset_id`, evidence ids, citations.
- Splat asset: `scripts/make_splat_asset.py`; PLY to the viewer PLY; sane prefix, core properties.

Both captures are y down (up `-y`); ingest detects and records the axis, floor slab (+1.069 boiler, +1.167 equipment) and evidence in `scene.npz`.

The 4 cm band is wider than the 2 cm splat slab: a narrower band leaves a shell that keeps the room connected, which is why the band is 4 cm and why it was never enough on its own. The band no longer decides alone what is removed: a point leaves the cloud only when it is in the band and the normal-or-thin-sheet gate agrees, so the same band keeps the floor and leaves a machine face alone.

## 3. Semantic extraction

Extraction voxelises at `max(3 cm, 1.4 x floor spacing)`, because a 26-connected graph needs that scale. Before that it removes the room's planes, and the plane stage is what decides whether an object survives. A horizontal plane is gated: a gaussian is removed only when it is inside the band and one of two independent tests agrees, either its own surface normal, the thinnest axis of its ellipsoid, matches the plane, or the column of points through it perpendicular to the plane is a thin sheet inside the band. A machine face crossed by a horizontal plane fails both however noisy its normals are: on the floor 46 percent of the band qualifies by normal, 84 percent by flat column and 90 percent by either, while on the machine's cross-section band removal falls from 100 percent in the first implementation to 14 percent. Vertical planes are proposed from the gaussians' own normals with their own budget and are removed with their whole band, gated or not, because a wall is a surface the room should not keep and a partly removed wall is a connected sheet that welds everything standing against it: the largest component fell from 24 percent of the capture to 3.8 percent once vertical planes were removed whole.

Components over the size limit are cut at a measured gap first, then at their thinnest neck, and only when neither exists at a counted quota cut, so every cut is reported as `splits_by_gap`, `splits_by_neck` or `splits_by_quota`. Boxes are fitted with 0.5 to 99.5 percentile extents; an object that stands on the floor gets an upright frame with the scene's up axis fixed and only yaw free, which is what the chair and the machines need, while a hanging pipe or a flat thing keeps the free PCA frame. A standing box whose fitted bottom is under the floor is lifted to it and one whose bottom is above it is extended down, 67 boxes on the complete capture. The class is a proposal among shape names from aspect ratio, extents, footprint and height, not an identity.

`classes.py` then makes the identity claims that shape cannot support. A valve proposal needs a pipe or duct box within 0.50 m to be fitted into, and a pump, motor, machine, drum, cabinet or pallet needs the floor or a supporting box underneath. Where neither holds, the class becomes `object` and `class_reason` says which test failed, because a generic label that is true beats a specific one that is not. Where an object matches an instance from the multi-view fusion, the fusion's class is used at confidence 0.9 and the reason names the views and the score. On the complete capture this names 8 objects and turns 25 unsupported identity labels into `object`.

## 4. Mapping

Each of the 30 assets gets one record. Candidates score `0.7 x class + 0.3 x size compatibility`, with two hard gates: score at least 0.6 and size compatibility at least 0.5, so class alone cannot carry a wrongly sized object. A proposed object leaves the pool; one object never hosts two tags. Records are `proposed` or `unresolved`; unresolved has no object, no score and a reason. The score is an uncalibrated prior, not a probability, and nothing is confirmed. The brief allows random mapping; that is not an excuse for false claims: the assignment is still only class-and-size evidence.

## 5. Navigation

`route.json` comes from an occupancy grid constructed from four independent layers, each of which is counted in the artifact. A cell is walkable ground only when it holds a gaussian within 0.08 m of the floor plane, so the planner cannot leave the observed room for the unobserved space behind a wall. A cell is blocked when a near-vertical surface crosses the robot's body: the normal of each gaussian is the thinnest axis of its ellipsoid, a wall runs at least 1.20 m up a 2.00 m band with no vertical gap over 0.20 m and starts within 0.35 m of the floor, while an overhead horizontal pipe starts too high to qualify. Object boxes block their footprints when the envelope is plausible for a single object, because a merged envelope that covers six square metres is not a machine; the skipped boxes are counted. Overhead horizontal structure blocks a taller robot only. The blocked layer is closed by one cell before the 0.10 m grid is inflated once by 0.20 m agent radius plus 0.02 m margin. A* is 8-connected and penalises low clearance. Clearance is the distance transform to the inflated boundary plus the radius, minimised over the corridor excluding the 0.9 m docking approach, so it is measured to the object surface. Before the floor and wall layers, the planner treated the room's open perimeter and the floor behind it as walkable: on the complete capture 57 free floor cells were reachable only by crossing a wall, and after the change it is zero. `test_walkable_walls.py` pins the behaviour with a doorway, a solid wall and a pipe a tall robot must go around, and it fails on the previous implementation.

## 6. Diagnosis

`diagnosis.json` joins `pack.json`, the converted workbook, on `asset_id`, carrying target, condition, health, issue, findings with evidence ids, telemetry, alarms, data-quality cases, citations and next check. For P-005: `attention_required`, health 44, `FOULING`, high urgency, 2 findings, 144 telemetry rows, 34 alarms, 9 data-quality cases, 2 cited documents, next check `inspect hydraulic path` cited to `DOC-FIELD-SAFETY`. It is retrieval plus rules, not a generative model: every statement is a join or template over a stable row id, and confidence is the pack's model confidence minus 0.05 per quality case, capped at 0.35. A generative model could write beyond the rows; this cannot invent a cause or explain one the pack lacks.

`reasoning` explains the condition instead of restating it. `facts` holds the first and last value of six channels over the asset's window and their percentage change, read from the same rows as the evidence. Five claims are generated from those facts, each citing evidence ids the artifact already publishes. Three hypotheses follow, with verdicts computed from the facts against named thresholds: `FOULING_FLOW_DROP_PCT` 10, `FOULING_SPEED_STABLE_PCT` 1, `FOULING_PRESSURE_STABLE_PCT` 1 and `SENSOR_DRIFT_CURRENT_RISE_PCT` 3, each chosen from the window change a fault makes against the scatter this pack carries. Hydraulic path fouling is supported when flow falls while speed and pressure hold; a restricted suction line or a partly closed valve is less likely when the head does not collapse; flow sensor drift is less likely when the motor load rises with a falling flow. A verdict falls back to `cannot separate` when the data does not clear its bar, and the sentence then says what the series does not show. `guardrail` reports how many claims carry a resolvable evidence id, so the artifact states its own coverage, and the test suite recomputes every fact from the pack and asserts the two agree.

## 7. Viewer

The room view is React and Vite in `app/web/src/room/`. One three.js scene with three.js 0.180 and `@sparkjsdev/spark` 2.4: `SparkRenderer` draws the `SplatMesh` from `/api/splat`. Boxes, route, robot and proximity colours are drawn in the same scene by the same camera. The robot is a 0.44 x 0.30 x 0.32 m marker at 0.5 m/s; the follow camera sits 2.6 m behind and 1.4 m above it. Every 500 ms the viewer highlights frames within 2.5 m. On arrival it fetches the diagnosis. It reads `/api/scene/objects`, `/api/scene/mapped`, `/api/scene/route`, `/api/splat` and `/api/diagnosis`, served by `main.py`; the panel calls the assignment a proposal, not a confirmed identification.

## 8. Verification

`make test` runs the offline pytest suite; `make web-build` runs `tsc --noEmit` and `vite build`; `make check` runs `scripts/sinceai_check.mjs`; `make audit` prints the framing audit for a capture.

Boiler room: 1,506,136 declared and 502,483 sane (33 percent), `-y` up with the floor slab at +1.072, 16 planes (8 horizontal, 8 vertical) removing 63.3 percent of the points, 122 objects from 122 clusters with nothing capped, largest 1.5 percent, median 330 points, 3.7 s, 28 proposed and 2 unresolved with P-005 to OBJ-034, route 1.39 m with 2 path points and 0.62 m clearance, viewer 428,991 gaussians and 24,023,947 B. The capture is truncated, so only 15.2 square metres of its floor exists; the grid is flagged `saturated` and the route is a stand-off on the nearest reachable ground.

Equipment room: 1,676,481 sane and none dropped, `-y` up with the floor slab at +1.174, 16 planes (8 horizontal, 8 vertical) removing 42.8 percent of the points, 150 objects from 272 clusters with 122 capped, largest 4.2 percent, median 3,454 points, 22.0 s, 30 proposed and none unresolved with P-005 to OBJ-037, route 0.24 m with 2 path points and 1.00 m reported corridor clearance, viewer 1,386,351 gaussians and 77,636,108 B.

The framing audit: on the complete capture 23 of 150 boxes are under 0.40 m tall against 66 of 150 before the change, 65 of 150 float with nothing under them against 85, and 52.4 percent of the capture's points fall inside exactly one box against 49.3 percent. Against the fused instance, the best proposal box in a reviewed anchor's column has a mean height and bottom error of 0.43 m and a median of 0.19 m, against 0.57 m and 0.45 m before.

## 9. Limits and what we would do next

No scale check has passed: no door-like box was framed, so `units_are_metres` is false and distances are scene units; the 1.92 m clear height between the boiler room's floor and its ceiling plane means the units are not exact metres. Classes are proposals from shape and context, never identifications; the reviewed layer supplies the identity for the eight objects in it.

**The reviewed layer.** Eight objects: seven boxes from the proposal layer that survived a visual audit, and one office chair recovered by instance fusion. Each carries an observed type, an inferred function, a confidence and the evidence sentence behind the label. Instance fusion measures the same object from outside: masks from sixteen posed views, plus three close-ups for an object no room view sees, are lifted into 3D through the splat's own depth and fused by containment. That experiment ran on a GPU host with a scratch harness outside this repository, which is why it is evidence in the fixture rather than a stage in the demo path; the fixture records the boxes, the view counts, the scores and the measurements they produced, and nothing here runs at demo time. The depth claim is the part that matters: a mask pixel takes the gaussian the composited image shows at the 50 percent transmittance crossing, not the nearest splat grazing the pixel, so the mask lifts to the surface a reader sees instead of the fog in front of it. All seven original anchors carry a fused box. Five agree with the reviewed box along the vertical within 0.16 m, the scale of the percentile trim; the washing machine's reviewed box was the top band of a 0.88 m body, so its box is the fused one; the blue vessel's fused box is taller than the vessel because the masks include the fittings on top, so its reviewed box stands. Mean visible fraction over the sixteen views is 0.43 for the pipe run, 0.40 for the washing machine, 0.19 for the pump and motor, 0.11 for the blue vessel and for the hose, 0.07 for the red door and 0.04 for the floor cluster: a box records what is visible, and the fusion, not the box, is what closes the object.

**Depth models were evaluated and not integrated.** Google's ARCore Depth API, the approach that prompted the question, is a feature of Google Play Services for AR: it runs in a live session on a phone camera with device motion and exposes no downloadable model or desktop runtime, so it cannot be applied to a trained capture offline. The closest downloadable Google model, TIPSv2-B/14 with a DPT depth head (Apache 2.0, 268 M parameters, metric depth at 448 by 448), runs at 24 to 29 ms per view on a 4090 and 36 to 42 s per view on this CPU, and it loses to the splat's own depth on every boundary measure tried. On six rendered views, 0 percent of anchor silhouette pixels have a model depth edge within one pixel against 52 percent for the splat; occlusion-boundary F1 is 0.021 against 0.137, and 0.144 against 0.175 when both are given an equal edge budget; Spearman agreement is 0.14 median, negative in one orbit view; and where the capture renders a veil, which covers 50 to 89 percent of shown pixels, the model sits closer to the near claimant than to the surface behind it in five of six views. The 27 MB Depth Anything V2 small already in the repository matches or beats it, so this is the model class rather than the checkpoint. The half-framed object was never a depth failure: inside the washing machine's reviewed box the extraction deleted 1,602 of 6,749 points as a plane before clustering, while the rendered depth still contained the machine in every view.

**Occlusion in the viewer.** A frame, the route line and the robot are depth-tested against the capture, so they hide behind whatever the capture has in front of them, which is the behaviour ARCore's depth map exists to give. The depth comes from a second draw of the accumulated splats with colour writes off and an opacity cut of 0.08, because the alpha-blended colour pass writes no depth and the 0.01 cut lets the faint veils write depth across a wide footprint. That draw is fill bound, so it draws every second gaussian, which halves its cost and still leaves no gap a thin overlay can pass through. Selecting an object adds a cyan light to the splats inside its box through a splat edit in the capture's own frame, so the surface the box is masking lights up rather than only the box.

**Not covered.** The robot is a marker, not physics. No frame rate or browser benchmark was run. Next: a scale check from a door or a known plate, a labelled class sample to score the proposals against, and the same lifting over the proposal layer instead of the eight reviewed objects.

## 10. Dependencies and how to run

Python 3.12 or newer with uv. The demo path uses numpy, OpenCV (`cv2`), FastAPI, uvicorn and pydantic; the workbook reader uses the standard library. The web build uses React 18, Vite 5, TypeScript 5, three.js 0.180 and `@sparkjsdev/spark` 2.4; tests use pytest. Nothing runs on the network at demo time. Put the capture and `builder_pack.xlsx` in `data/supplied/`. `make demo` defaults to `CAPTURE=equipment` (the complete `Equipment Room.ply`), builds every artifact and the page, and serves both at `http://127.0.0.1:8000`; `make demo CAPTURE=boiler` runs the capture the brief names. `make test` and `make check` run the checks; `npm run build` also works; the Makefile uses pnpm.
